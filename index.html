The backbone of the session

Which layer are we talking about?

Credential security and reader-bus security are separate security problems.

Click each layer. Points this model untangles: a 26-bit format doesn't need a Wiegand connection; an OSDP reader can deliver 26-bit data; a DESFire EV3 chip doesn't tell you which application is on it; a reader can detect a card without the keys to its protected application; a reader can authenticate perfectly and still send data the controller decodes wrongly; a system can have secure credentials and an insecure reader link, or the reverse.

Credential families · layer 2

Two RF neighborhoods

Proximity, or “Prox”

  • Usually a static identifier
  • Generally no modern mutual authentication
  • Often chosen for compatibility, not credential security
  • An easy migration target when a customer modernizes
HID ProxIndalaAWIDEM family

“Prox” is a broad legacy family. HID Prox is the best-known one, but Prox does not mean HID.

125 kHz Prox solved convenience. It was not designed for the threat model we have today.

“The card works” and “the card is secure” are not the same thing.

13.56 MHz

13.56 MHz tells you the RF neighborhood. It does not tell you the security model.

A 13.56 MHz card can be a simple legacy implementation, or it can use modern cryptography and protected applications.

5–15 min. Don't teach RF physics. The tree is intentionally simplified: the goal is categories, not a smart-card standards lecture. Avoid saying every 125 kHz credential is identical or that every Prox product is HID.
Credential families · layers 3 and 4

HID, from Prox to Seos

The credential chip and the identity application are not necessarily the same thing.

Separate RF standard, credential technology, HID application and security model, and PACS output format. Legacy iCLASS should not be presented as equivalent to Seos. No need to go into published iCLASS attacks unless asked. The SIO-on-DESFire point is a strong demonstration of the layer model.
Credential families · layer 3

What “MIFARE DESFire” actually means

MIFARE
An NXP product brand and family, not a company
DESFire
A smart-card IC family sold under the MIFARE brand
Built on
ISO/IEC 14443A air interface and standard cryptography, including AES
Model
Multi-application: independent applications can share one card

DESFire is a broadly supported secure smart-card platform, not an open-source credential.

EV1 → EV2 → EV3 is an evolution

The chip version and the application profile are separate. Real interoperability depends on:

readerapplicationkeyscommandsconfiguration
Why DESFire feels "more open": many reader vendors support it, many access-control vendors build applications on it, and a customer can, in the right architecture, keep control of its own application and keys. That is very different from "open source". Don't teach "EV3 cards work with EV2 readers". Teach: an EV3 chip is designed for backward compatibility, but interoperability depends on reader, application, keys, commands and configuration.
Does EV3 automatically mean more secure?

Climb the security ladder

An EV3 card read only by its public identifier is not a high-security deployment. Select a rung.

The biggest security jump is not EV2 → EV3. It is static identity → properly authenticated secure credential.

With mutual authentication, AES protection and good key management, an EV2 implementation can already give very strong credential security. EV3 adds capabilities, but only the features actually used count.

Application versus chip · layer 4

One chip, many applications

Using DESFire does not automatically make a deployment open.

Seos ecosystemDESFire platform
More vendor-controlledMore multi-vendor use

Conceptual, not a scorecard. Both can support modern cryptographic access control. Open and secure are different axes.

Better “open architecture” questions

  • Who owns the credential keys?
  • Who can issue new credentials?
  • Can the customer change reader vendors?
  • Is the PACS ID portable, or does migration mean new cards?
2N PICard is not a competing card technology to DESFire; it is an application on it. Keep the DESFire vs Seos discussion to about three minutes. Avoid "which is secure, Seos or DESFire?". Both can be. The larger difference is the ecosystem and who controls the credential application and keys. Other good questions: can multiple applications coexist on the credential? Is the application spec available? Can another integrator manage the system later?
Reader compatibility

“It beeps” is not enough

Compatibility exists at seven levels. Select where the reader stops, and see the symptom it produces.

A beep proves RF interaction. It does not prove secure credential interoperability.

Example: modern HID Signo readers support combinations of HID Prox, iCLASS, Seos, MIFARE Classic, DESFire EV1/EV2/EV3, OSDP and Wiegand. So "the customer has HID readers" is not enough. Ask: which model, firmware or configuration, RF technology, UID/CSN or protected application, which secure application, who owns the keys, what does the reader output, Wiegand or OSDP?
Layer 5 or layer 6?

Why “Wiegand” causes so much confusion

Layer 6 · Transport

Wiegand as an interface

Classic reader wiring that carries credential data from reader to controller on data lines.

Layer 5 · PACS format

Wiegand as a format family

“26-bit Wiegand”, “37-bit Wiegand”: how the credential data is organized into bits.

Send the same 26-bit credential two ways

Reader
26-bit H10301 · FC 42 · CN 12345Wiegand · Data0/Data1 · one-way
ControllerFC 42 · CN 12345
Reader
26-bit H10301 · FC 42 · CN 12345OSDP · RS-485 · two-way, supervised
ControllerFC 42 · CN 12345

The payload is identical on both lanes. Either way, the controller still needs to know how to interpret the bits.

“26-bit” describes the data. “OSDP” describes how the reader communicates it.

One of the most important teaching sections. Demo 4: if the lab can't easily switch between Wiegand and OSDP, use this slide instead of rewiring hardware.

Layer 5 · PACS data format

A format is a way to read a row of bits

The raw bitstream doesn't carry a label that says “I am H10304”. The system has to know how to interpret it.

total bit lengthfacility code locationcard number locationparity locationsparity coveragefield sizesfield orderbit orderbyte orderdecimal or hex
parityfacility codecard number

Bit length tells you how much data arrived. Format tells you what the bits mean.

H10301 is HID's designation for the familiar open 26-bit format. H10302 and H10304 are both 37 bits and mean different things. "37-bit" is not a complete card-format definition.
Exercise · H10301

Decode a 26-bit card

Change the facility code or card number, flip any bit, or change how Secure Entry reads the fields.

parityfacility code fieldcard number fieldSelect a bit to flip it

Ask trainees to identify: total length, leading parity bit, facility code field, card number field, trailing parity bit. Then switch to "misconfigured" and ask: "If ACS thought bits 2–17 were the card number, would the reader fail?" No. The reader works perfectly; the controller interprets good data incorrectly. Leading parity is even over bits 1–13; trailing parity is odd over bits 14–26.
Secure Entry custom card formats

Right bits, wrong direction

Two readers send the same credential. Secure Entry expects 0xFB4C. Pick a reader, then fix the interpretation.

The reader may be sending the right bits, but the controller may be reading them in the wrong direction.

A custom format in Secure Entry can set

  • Bit length from 1 to 256
  • Invert bit order
  • Invert byte order, when the length divides by 8
  • Card number and facility code fields and their ranges
  • Decimal or hexadecimal output
  • Big-endian or little-endian per field
Demo 3. The card did not change, and the reader is not necessarily broken: the problem is representation. Endianness answers which end of a multi-bit or multi-byte value is treated as the significant end. No computer-science lecture needed.
A Secure Entry rule

Only one active format per bit length

37 raw bits arrive. Nothing in them says which 37-bit format they are. Try switching on a second one.

From the reader

Don't generalize this to "no access-control system can support two formats of the same length". Some systems use reader-specific configuration or credential metadata to separate them. The ACS-specific rule is the teachable point. Symptom to remember: one 37-bit card population works and another doesn't.

    Must understand before leaving: 1) credential technology ≠ card format ≠ reader protocol; 2) 125 kHz vs 13.56 MHz is one layer; 3) Wiegand is both an interface and a format family; 4) OSDP is transport, not a credential; 5) 26-bit doesn't mean Wiegand wiring; 6) bit length doesn't uniquely identify a format; 7) Secure Entry can define detailed custom formats; 8) one active format per bit length; 9) a beep ≠ a secure application read; 10) troubleshoot one layer at a time.
